## 1. 项目概述：这个东西到底是干嘛的？

### 1.1 一句话说明

**这是一个"AI 问题代答总台"。**

你把问题发给它，并告诉它"这个问题请交给某某 AI 回答"，它就会帮你把问题转交给对应的人工智能（比如 DeepSeek、Kimi、通义千问、ChatGPT，或者你自己电脑上运行的 AI），拿到回答后，再用统一、整齐的格式交还给你。

### 1.2 为什么需要它？——先讲个生活故事

想象一栋写字楼里有 6 家不同的餐厅：

- 中餐厅（DeepSeek）、面馆（Kimi）、快餐店（通义千问）……每家门禁卡不一样，菜单格式也略有差别；
- 西餐厅（ChatGPT、Claude 等）在国外，电话很难直接打通，需要通过一家"国际订餐平台"统一转接；
- 你家里自己还开了个小厨房（本地私有模型），不要钱，但只对你自己开放。

如果让每个顾客（也就是你的网站、App、小程序）**自己一家一家去记**：这家电话是多少、门禁卡长什么样、菜单怎么填……会非常痛苦。而且门禁卡（就是后面要讲的 **API Key**，可以理解为"消费密码"）直接塞在顾客手里，一旦泄露，别人就会刷爆你的账户。

于是我们在中间设了一个**统一订餐总台**：

- 顾客**只需要联系总台**，说："给我来份 `deepseek-chat` 套餐，问题是『今天天气怎么样』"；
- 总台翻开**通讯录**查到这道菜归哪家厨房；
- 总台替顾客刷**自己保管的门禁卡**，把问题翻译成那家厨房看得懂的格式，送过去；
- 厨房做好后，总台装进**统一的外卖袋**里交还给顾客。

这就是 MODEX 这个项目做的事情。只不过"餐厅"换成了各家**大模型**（可以对话的人工智能服务），"总台"就是这个项目——一个常驻运行、专门负责**接单、转接、收回答、回消息**的"后端服务"。

> **两个词先解释：**
> - **后端服务**：一个在电脑（或服务器）上默默运行、不直接给人看界面、专门接收其他程序请求并干活的程序。就像餐厅后厨，顾客看不见它，但所有菜都出自这里。
> - **大模型**：一种能听懂人类语言、能回答问题、能写文章的人工智能程序。比如 DeepSeek、ChatGPT 都是。本书后文统称"AI"。

### 1.3 它面向谁使用？

| 使用者 | 他们怎么用它 |
| --- | --- |
| **网站 / App / 小程序开发者** | 自己的产品只对接这一个总台，就能随意切换几十种 AI，不用分别对接几十次 |
| **公司 / 团队** | 把所有 AI 的消费密码集中保管在服务器上，员工和访客接触不到，安全可控 |
| **AI 应用学习者** | 通过这个结构清晰的小项目，一次看懂"一个互联网服务是怎么搭起来的" |
| **隐私敏感的用户** | 涉密问题可以走自己电脑上的本地 AI，不出内网，总台同样一套方式调用 |

### 1.4 它的核心价值（为什么这个设计值得学）

1. **只记一个电话**：前端（给人看的网页/App 那一面）只对接这一个总台，想换 AI 时只改一个"套餐代号"，代码几乎不用动。
2. **密码不出门**：所有 AI 的消费密码都锁在总台的配置抽屉里，不暴露给浏览器和用户。
3. **三类 AI 统一管理**：国内的、国外的、本地的 AI，接入方式各不相同，但总台把差异全部"消化"掉了，调用者感知不到差别。
4. **加新店不用重新装修**：以后出现新的 AI 厂商，只要新增一个小文件"登记"一下，总台的核心流程一行都不用改——这是工程设计里非常重要的"对扩展开放"思想。

### 1.5 阅读本书前的"名词翻译卡"

先扫一眼，有个印象即可，后文用到时还会再解释。

| 你会看到的词 | 大白话翻译 |
| --- | --- |
| 前端 | 给用户看、用户点按操作的界面（网页、App） |
| 后端 | 在服务器上默默干活的程序，本项目就是一个后端 |
| API | 程序与程序之间约定好的"服务窗口"，类似银行柜台：你按格式递单子，它按格式给结果 |
| API Key | 使用某家 AI 服务的"消费密码/门禁卡"，按调用量计费，必须保密 |
| 模型 | 这里指某一家 AI 的某个具体型号，类似"iPhone 16"和"iPhone 16 Pro"是不同型号 |
| mode（模式） | 本项目给每个 AI 套餐起的内部代号，比如 `deepseek-chat` |
| 路由 | "根据代号查出去找哪家"这个转接动作 |
| 适配器 | 总台里专管某一家 AI 的"对接翻译员" |
| JSON | 一种所有程序都认识的"标准表格格式"，长得像带标签的填空表 |
| 端口 | 一台电脑上每个服务的"窗口编号"，本项目默认用 **8000 号窗口** |

## 2. 整体架构说明：它由哪些部分组成？

### 2.1 核心类比：总台的 6 个角色

请记住下面这家"AI 问题代答总台"的分工，后文每个文件夹都对应其中一个角色：

| 角色 | 项目里的对应部分 | 职责（大白话） |
| --- | --- | --- |
| **大门与接待员** | API 接口层 | 顾客从唯一的大门进来，接待员负责收单子、发回外卖袋 |
| **表格质检员** | 参数校验模块 | 检查顾客填的单子合不合规：问题写了没有？温度有没有乱填？ |
| **通讯录** | 路由表（`config/routes.json`） | 一本"套餐代号 → 哪家厨房"的对照表，可随时增删页 |
| **排班经理** | 路由分发服务（核心大脑） | 查通讯录、叫对应翻译员、合并所有要求、统筹全程 |
| **翻译员花名册** | 适配器注册表 | 登记每位"厂商专属翻译员"的名单，排班经理按名字点人 |
| **翻译员队伍** | 适配器层 | 每位翻译员专懂一家厨房的规矩，负责送问题、收菜、翻译回标准语言 |
| **钥匙柜** | 配置模块（`.env` 文件） | 存放各家厨房的门禁卡（API Key），只有总台自己能开 |
| **标准外卖袋** | 统一响应模块 | 不管哪家做的菜，都装进一模一样的袋子，附追踪编号 |
| **投诉处理员** | 异常处理模块 | 厨房关门、门禁卡失效、单子填错……都按统一话术礼貌回应 |

### 2.4 为什么这样分？——"部门独立"的好处

把"接待、质检、排班、翻译、钥匙、投诉"分成独立部门，最大的好处是：

- **换招牌不动厨房**：想把外卖袋样式改好看一点，只动 `schemas/`；
- **加厨房不动大堂**：多了一家新 AI，只在 `adapters/` 添一个翻译员、在通讯录加一行；
- **查问题很容易**：单子不合格，一定是质检科的事；密码报错，一定去钥匙柜查。

这就是工程上常说的**分层**和**关注点分离**——不用记这个名词，记住"一个部门只管一件事"即可。

## 3. 核心功能拆解：它具体能做什么？

下面每一项功能都对应真实代码，括号里给出了文件位置，方便你日后去代码里"按图索骥"。

### 3.1 功能一：开一个统一窗口接收请求

- **是什么**：总台在 8000 号窗口营业，任何人只要按规定格式递单子，总台就受理。
- **窗口地址**：`POST /api/v1/chat/completions`（这是主窗口，专门收问题）
- **生活场景**：就像快递柜只有一个投递口，不管你寄哪家快递，都先从这个口放进去。
- **代码位置**：`app/api/v1/endpoints/inference.py`

顾客递的单子（JSON 表格）长这样，每个格子后面都有中文解释：

```json
{
  "mode": "deepseek-chat",
  "prompt": "请用三句话介绍杭州",
  "temperature": 0.7,
  "max_tokens": 500
}
```

| 格子名 | 含义 | 不填会怎样 |
| --- | --- | --- |
| `mode` | **必填**。想找哪家 AI 的套餐代号 | 不填直接被质检员退回 |
| `prompt` | 你的问题（单轮对话时用它） | `prompt` 和 `messages` 至少填一个 |
| `messages` | 多轮对话记录，适合"你一言我一语"的连续聊天 | 与 `prompt` 二选一 |
| `temperature` | "想象力旋钮"，0～2 之间。越低越稳重严谨，越高越发散有创意 | 用通讯录里给该套餐预设的值 |
| `max_tokens` | "字数上限"，控制回答最长能写多少 | 用 AI 厂商自己的默认值 |
| `top_p` | 另一个更高级的"选词风格旋钮"，新手一般不用动 | 不限制 |
| `stop` | 停止词：AI 写到这些词就停笔 | 不设置 |
| `stream` | 是否要"挤牙膏式"逐字吐回答（像 ChatGPT 官网打字效果） | 当前版本只支持一次性返回 |
| `user` | 给最终用户编个号，方便厂商排查滥用 | 不传 |

**实际场景举例**：

- 学生写作业求严谨 → `temperature: 0.2`
- 广告文案要创意 → `temperature: 1.2`
- 客服机器人回答要短 → `max_tokens: 100`

### 3.2 功能二：表格质检员——参数自动校验

- **是什么**：单子进入后，质检员（Pydantic，技术栈章节会解释）逐项检查：
  - `mode` 填了吗？是不是空字符串？
  - 问题和对话记录不会都空着吧？
  - `temperature` 有没有超过 2、低于 0？
  - `max_tokens` 是不是大于 1 的整数？
- **使用效果**：不合格的单子**根本进不了厨房**，当场带着详细原因退回，不会浪费一次 AI 调用费。
- **场景举例**：你把温度填成 `3`，会立刻收到：

```json
{
  "code": 4000,
  "message": "请求参数校验失败",
  "data": [{"msg": "Input should be less than or equal to 2", "...": "..."}]
}
```

  连第几格错了、为什么错都写得清清楚楚。
- **代码位置**：`app/schemas/chat.py`

### 3.3 功能三：查号转接——按 mode 路由到对应 AI

这是整个项目的**核心动作**。

- **是什么**：排班经理拿到 `mode`，翻开通讯录 `config/routes.json`，查到这家厨房的三条关键信息：
  - `provider`：属于**国内 / 国外 / 本地**哪一类（决定走哪条通道、用什么钥匙）；
  - `vendor`：具体厂商是谁（决定叫哪位翻译员）；
  - `model`：厨房里的**真实菜名**（有些代号对外好听，对内要报官方型号）。
- **通讯录里现在登记的 9 个套餐**：

| 套餐代号 mode | 类别 | 厂商 | 实际报给厨房的型号 |
| --- | --- | --- | --- |
| `deepseek-chat` | 国内 | DeepSeek | `deepseek-chat` |
| `deepseek-reasoner` | 国内 | DeepSeek | `deepseek-reasoner`（推理增强版） |
| `moonshot-v1-8k` | 国内 | Moonshot（Kimi） | `moonshot-v1-8k` |
| `qwen-plus` | 国内 | 阿里通义千问 | `qwen-plus` |
| `glm-4` | 国内 | 智谱 | `glm-4` |
| `gpt-4o` | 国外 | Router 平台转接 | `openai/gpt-4o` |
| `claude-3.5-sonnet` | 国外 | Router 平台转接 | `anthropic/claude-3.5-sonnet` |
| `local-qwen2.5` | 本地 | 本机 Ollama | `qwen2.5:7b` |
| `local-vllm-qwen2.5` | 本地 | 本机/内网 vLLM 服务 | `Qwen2.5-7B-Instruct` |

- **场景举例**：顾客只说 `gpt-4o` 三个字母，经理就知道：这要走国外通道 → 叫 Router 翻译员 → 刷国际平台的全局卡 → 报上的正式菜名是 `openai/gpt-4o`。
- **代号不存在怎么办**：比如填了 `mode: "xxx"`，经理查不到，立刻返回 404 号回复（404 是"查无此号"的行业暗号，下文细讲），还贴心地附上当前**全部可选代号清单**。
- **代码位置**：路由表 `app/core/config.py`，分发逻辑 `app/services/inference_service.py`

### 3.4 功能四：三类模型的差异化接入（本项目的重头戏）

#### A. 国内厂商：每家一把独立钥匙，一位专属翻译员

DeepSeek、Kimi、通义千问、智谱四家，各自有独立账户、独立密码（`DEEPSEEK_API_KEY`、`MOONSHOT_API_KEY`……）。

经理对国内通道的规矩是：**找哪家就刷哪家的卡**。如果对应卡片是空的，直接返回标准提示："未配置国内厂商 deepseek 的 API Key"，并告诉你该去 `.env` 文件补哪一条。

#### B. 国外厂商：统一走第三方"国际平台"Router

ChatGPT、Claude 等国外 AI 不直接对接，而是全部通过一家叫 **Router（路由平台，示例用 OpenRouter）** 的中间商：

- 顾客和总台都只持有**一张全局平台卡** `ROUTER_API_KEY`；
- Router 平台在海外替我们连通几十家国外 AI，账单统一结算；
- 新增任何一家国外 AI，都**不需要新翻译员、不需要新卡**，只需在通讯录加一行、写上平台要求的"厂名/型号"即可。

#### C. 本地私有化模型：不上网、不花钱、不泄密

- 对应翻译员对接你电脑（或公司内网）上自己跑的 AI 服务，示例默认对接 **Ollama**（一个能让普通人在自己电脑上运行开源 AI 的工具，地址 `http://localhost:11434/v1`）；
- **不需要门禁卡**；
- 如果通讯录里写了 `base_url`，还可以改指到内网的 vLLM 等其他自建服务（示例中的 `local-vllm-qwen2.5` 就是接到 8000 端口的另一个本地服务）；
- 涉密内容不出内网，这是企业最看重的一点。

> 小知识：这三类 AI 虽然来自不同公司，但它们绝大多数都采用了同一套"说话规矩"（行业里叫 **OpenAI 兼容协议**，因为 OpenAI 最早定了这套格式，后来大家都跟着学）。所以翻译员们共享一本《标准翻译工作法》（`openai_compatible.py`），每位具体翻译员只需要声明"我这家的地址是什么、怎么刷卡"，几行代码就上岗了。
> 如果将来接入一家"不说普通话"的厂商（比如用自家特殊规矩的），只要为它单独写一位翻译员即可，其他人完全不受影响。

### 3.5 功能五：三级"要求合并"——谁的要求说了算？

同一个参数（比如温度）有三个来源可能给值，项目规定的优先级是：

```
顾客单子上明写的值        （最高优先级）
        ↑ 没写才看
通讯录里该套餐的预设值     （模型级默认值）
        ↑ 也没有才用
总台的兜底默认值          （温度最终兜底为 1.0）
```

**场景举例**：通讯录里给 `deepseek-chat` 预设了温度 0.7；顾客这次想要更稳重，明写 0.2 → 最终按 **0.2** 送进厨房；顾客不写 → 用 0.7。

### 3.6 功能六：统一外卖袋——任何 AI 的回答都长一个样

无论哪家 AI 做的回答，回到顾客手里都是**同一种袋子**：

```json
{
  "code": 0,
  "message": "success",
  "request_id": "8625f043c62940d0866528cb64023f96",
  "data": {
    "id": "chatcmpl-abc123",
    "mode": "deepseek-chat",
    "model": "deepseek-chat",
    "choices": [
      {
        "index": 0,
        "message": {"role": "assistant", "content": "杭州是……"},
        "finish_reason": "stop"
      }
    ],
    "usage": {"prompt_tokens": 12, "completion_tokens": 88, "total_tokens": 100},
    "created": 1776000000
  }
}
```

袋子各区域说明：

| 区域 | 含义 |
| --- | --- |
| `code` | 业务状态码，**0 代表成功**，其他数字代表不同类型的问题 |
| `message` | 文字状态说明 |
| `request_id` | 本次服务的**追踪编号**，每次都不一样，出问题时报这个号可以精准查日志 |
| `data.choices[0].message.content` | **AI 的回答正文在这里** |
| `data.usage` | 这次问答花了多少 token（可以粗略理解为 AI 计量用的"字数单位"），方便核算费用 |

统一格式的好处：顾客的解析代码只写一次，今天接 DeepSeek、明天换 Claude，**取回答的代码一行都不用改**。

### 3.7 功能七：投诉处理科——出任何意外都有体面回应

项目预设了 7 种常见事故，每种都有固定的**状态码 + 解释口径**，绝不会把程序崩溃时那种吓人的英文堆栈直接甩给顾客：

| 情况 | 状态码 | 顾客看到的说明（示例） |
| --- | --- | --- |
| 单子格式不合格 | 422 / 4000 | 请求参数校验失败（附具体哪一格错） |
| 套餐代号查不到 | 404 / 4040 | 不支持的模型调用模式（附可选清单） |
| 忘了配某家的钥匙 | 500 / 5002 | 未配置国内厂商 deepseek 的 API Key |
| 厨房说门禁卡无效 | 502 / 5021 | 上游模型服务认证失败 |
| 厨房内部报错 | 502 / 5022 | 上游模型服务调用失败 |
| 厨房电话打不通/超时 | 503 / 5030 | 上游模型服务暂不可用 |
| 点了"逐字流式回答" | 501 / 5010 | 当前版本暂不支持流式输出 |
| 没预料到的其他错误 | 500 / 5000 | 服务内部错误（详细内情只写进内部日志） |

另外还有两个细节：

- 每次请求进门时，总台会发（或沿用顾客带来的）一个 `request_id` 追踪编号，回复时放在袋子上、也写进响应头，像快递单号一样全程可追；
- 值班日志本（`app/utils/logger.py`）会记录每次转接：转给了谁、什么时间、出了什么事，方便事后复盘。

### 3.8 功能八：问讯处——健康检查接口

- **窗口地址**：`GET /api/v1/health`
- **作用**：任何人访问这个地址，立刻知道总台是否还在营业、当前通讯录里有几个套餐、翻译员花名册上有谁。
- **场景举例**：运维人员想确认服务器上的服务"是死是活"，访问一下即可，不用真的花钱问 AI；监控系统也可以每隔几秒自动问一次，发现断了立刻报警。

### 3.9 功能九：自带一份"在线说明书"（Swagger 文档）

总台挂着一块**电子招牌**：服务启动后，用浏览器打开 `http://127.0.0.1:8000/docs`，会看到一个自动生成的说明书网页：

- 列出所有窗口、每个格子的含义、是否必填；
- 可以直接在网页上填单子、点按钮**免费试用**，不用写任何代码；
- 这份说明书永远和真实代码同步，因为它是程序根据质检规则**自动生成**的。

这是零基础读者动手体验本项目最友好的入口。

### 3.10 功能十：加一家新 AI 极其简单（可扩展性）

以新增"豆包"或任何一家新厂商为例，只需 3 小步，**不动任何核心流程**：

1. 在 `app/adapters/domestic/` 下新建一个小文件，照抄现有翻译员模板，改个厂商名和地址；
2. 在 `app/adapters/__init__.py` 花名册里加一行"报到"；
3. 在 `.env` 加一条钥匙、在 `config/routes.json` 通讯录加一行代号。

新增国外 AI 更简单——只做第 3 步即可（共用 Router 翻译员和全局卡）。

## 4. 运行流程演示：一次完整服务是怎么发生的？

本章带你从零开始，完整走一遍真实流程。以下命令均在 Windows 的 PowerShell 中执行。

### 4.1 第一步：领工具（安装软件环境，只需一次）

1. 电脑上需要安装 **Python 3.11**（运行本项目的"引擎"，可到 python.org 免费下载，安装时勾选 *Add Python to PATH*）。
2. 在项目文件夹 `e:\Code\modex` 中创建一个**独立工具间**（虚拟环境，避免和电脑上其他项目的工具互相打架）：

   ```powershell
   python -m venv .venv
   ```

3. 按清单领工具（依赖包，即别人写好、我们直接用的现成工具）：

   ```powershell
   .\.venv\Scripts\python.exe -m pip install -r requirements.txt
   ```

   > 本项目创建时这一步已经执行过；若你是新克隆的项目，需要执行一次。

### 4.2 第二步：配钥匙（填写 API Key）

1. 复制 `.env.example`，改名为 `.env`。
2. 用记事本打开 `.env`，把你申请到的密码填到对应行的等号后面。例如：

   ```text
   DEEPSEEK_API_KEY=sk-你从DeepSeek官网申请到的真实密码
   ROUTER_API_KEY=sk-or-你从OpenRouter申请到的全局密码
   ```

3. **只想体验、暂时没有任何密码？** 没关系——服务照样能启动，你可以：
   - 先看健康检查、在线说明书；
   - 故意触发各种错误，观察统一回复；
   - 若你在本机装了 Ollama 并下载了模型，可直接免费体验 `local-qwen2.5`。

> 安全提醒：`.env` 是密码本，**永远不要**发到网上、传到 Git 仓库或发给别人。

### 4.3 第三步：开门营业（启动服务）

在项目目录执行：

```powershell
.\.venv\Scripts\python.exe run.py
```

你会在日志中看到类似这样的关键一行，说明启动成功：

```text
应用启动完成：加载 9 条模型路由 -> claude-3.5-sonnet, deepseek-chat,
deepseek-reasoner, glm-4, gpt-4o, local-qwen2.5, local-vllm-qwen2.5,
moonshot-v1-8k, qwen-plus
```

**这一刻后台发生了什么？**

1. 打开钥匙柜 `.env`，把每条钥匙读到内存里；
2. 翻开通讯录 `routes.json`，登记好 9 个套餐；
3. 翻译员们全部到花名册签到；
4. 8000 号窗口正式开放。

停止服务：在窗口里按 `Ctrl + C`。

### 4.4 第四步：发出第一笔请求（三种方式任选）

**方式 A（最推荐零基础）：用在线说明书**

浏览器打开 `http://127.0.0.1:8000/docs` → 找到 `/api/v1/chat/completions` → 点 *Try it out* → 把示例内容贴进输入框 → 点 *Execute*，下方直接看到回复。

**方式 B：让前端程序用代码发请求**（这是真实业务中的用法），JavaScript 示例：

```javascript
fetch("http://127.0.0.1:8000/api/v1/chat/completions", {
  method: "POST",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({
    mode: "deepseek-chat",
    prompt: "请用三句话介绍杭州",
    temperature: 0.7,
    max_tokens: 500
  })
})
  .then(res => res.json())
  .then(result => {
    // AI 的回答正文：
    console.log(result.data.choices[0].message.content);
  });
```

**方式 C：用 PowerShell 命令行直接发**：

```powershell
Invoke-RestMethod -UseBasicParsing -Method Post `
  -Uri http://127.0.0.1:8000/api/v1/chat/completions `
  -ContentType 'application/json' `
  -Body '{"mode":"deepseek-chat","prompt":"请用三句话介绍杭州","temperature":0.7}'
```

### 4.5 第五步：拆开一份成功回复

成功时你会收到 3.6 节展示过的那种统一外卖袋。重点取三个位置：

- `data.choices[0].message.content` → 给用户看的回答正文；
- `data.usage.total_tokens` → 本次消耗，用于成本核算；
- `request_id` → 出问题时拿着它找技术人员查日志。

### 4.6 一次请求在总台内部的完整旅程（10 个步骤）

```
顾客                大门接待员   质检员   排班经理   通讯录  花名册  翻译员   AI厨房

 │                   │──────────────────▶│         │      │       │       │
 │                   │          │        │③查代号   │      │       │       │
 │                   │          │        │────────▶│      │       │       │
 │                   │          │        │ 国内/DeepSeek/deepseek-chat    │
 │                   │          │        │◀────────│      │       │       │
 │                   │          │        │④点翻译员 │      │       │       │
 │                   │          │        │─────────────────▶│       │       │
 │                   │          │        │⑤取卡片+合并温度等要求│       │       │
 │                   │          │        │────────▶钥匙柜    │       │       │
 │                   │          │        │⑥把单子交给翻译员    │       │       │
 │                   │          │        │─────────────────▶│       │       │
 │                   │          │        │         │      │ ⑦翻译成厨房格式│
 │                   │          │        │         │      │──────▶│       │

 │                   │          │        │  装统一外卖袋     │       │       │
 │  ⑩拿到外卖袋       │◀─────────┴────────┴─────────┴──────┴───────┘       │
 │◀──────────────────│                                                    │
```

逐步骤对应：

1. **接单**：请求抵达 8000 窗口，中间件先给这次服务发一个 `request_id` 编号（像取号机取票）；
2. **质检**：Pydantic 按 `chat.py` 的规则逐项验表，不合格立即退回；
3. **查通讯录**：经理用 `mode` 在 `routes.json` 查出类别、厂商、真实型号；
4. **点翻译员**：到花名册 `registry.py` 点名对应适配器，没点到（配置错了）则报 5001；
5. **取钥匙**：国内取该厂商独立 Key、国外取全局 Router Key、本地无需卡——缺卡报 5002；
6. **合并要求**：按 3.5 节的三级优先级算好温度、长度等最终参数；
7. **翻译并送出**：适配器把标准单子变成该厨房的格式，用 httpx（跑腿员）发 HTTP 请求；
8. **AI 推理**：厨房思考并回答（真正耗时主要在这一步）；
9. **回收与翻译**：适配器收到回答，解析成统一的 `ModelOutput`，异常（401 卡失效、超时等）在此翻译成对应事故码；
10. **封装交付**：经理装进统一外卖袋，接待员交还顾客，同时日志本记录全程。

### 4.7 故意出错：看看系统的"教养"

| 你试着这样发 | 你会收到 |
| --- | --- |
| 请求体写成 `{}` | 422 + 4000，提示 `mode` 必填 |
| 温度填 3 | 422 + 4000，提示必须 ≤ 2 |
| `mode: "abc"` | 404 + 4040，并列出 9 个正确代号 |
| 不填 Key 调 `deepseek-chat` | 500 + 5002，告诉你该补哪条环境变量 |
| 调 `local-qwen2.5` 但本机没开 Ollama | 503 + 5030，上游服务暂不可用 |
| `stream: true` | 501 + 5010，流式功能尚未开放 |

这说明系统对"乱来"是有充分预案的——这在真实项目中叫做**健壮性**。

## 5. 技术栈说明：用了哪些工具，各管什么事？

不用记住名字，只要知道每个工具"在故事里扮演谁"：

| 技术（真实名称） | 生活类比 | 在本项目里负责什么 | 零基础记忆法 |
| --- | --- | --- | --- |
| **Python 3.11** | 总台使用的"工作语言" | 所有部门的员工都用这门语言沟通 | 地基 |
| **FastAPI** | 一套精装修的"餐厅开店套餐" | 帮你快速开出标准窗口、自动生成在线说明书、自动挂质检流程 | 房子的框架 |
| **Uvicorn** | 真正"开门营业"的值班领班 | 把程序跑起来、在 8000 窗口持续听有没有顾客敲门 | 营业窗口 |
| **Pydantic** | 表格质检员 | 按规则逐格验收输入表格、并把回复装进规范袋子 | 质检员 |
| **pydantic-settings + .env** | 带标签的钥匙柜 | 启动时从 `.env` 文件读取密码和设置，代码里不写死密码 | 保险柜 |
| **httpx** | 腿脚勤快的跑腿员 | 替翻译员给远端 AI 厨房打电话、等回复、处理超时 | 外卖骑手 |
| **JSON** | 全行业通用的标准表格 | 顾客递单、厨房回单都用这种格式 | 普通话表格 |
| **Ollama / vLLM** | 你家自己的小厨房 | 在自己电脑/内网把开源 AI 真正跑起来 | 自备锅灶 |
| **OpenRouter** | 国际订餐平台 | 在海外统一接通 ChatGPT、Claude 等，只刷一张平台卡 | 海外代购 |
| **Swagger UI** | 门口的电子说明书 | `/docs` 自动生成、可直接试用的交互文档 | 电子菜单 |
| **虚拟环境 venv** | 每个项目独立的工具间 | 项目间工具版本互不干扰 | 独立工具箱 |

**它们之间怎么配合？** 一句话：

> Python 是语言；FastAPI 定义窗口与流程；Uvicorn 让它跑起来持续营业；Pydantic 把好进出门质量关；`.env` 保管密码；httpx 出门跑腿；JSON 是所有表格的通用格式；Ollama/Router 是三类厨房的具体通道。

## 6. 常见疑问解答

### 关于"这是什么"

**Q1：我完全不懂代码，能用起来这个项目吗？**
能。最低门槛的玩法：装好环境、配好 `.env`、执行启动命令，然后打开 `http://127.0.0.1:8000/docs`，在网页上填问题点按钮，就能用。代码一行都不用写。

**Q2：这个项目本身是 AI 吗？它会回答问题吗？**
它**不是** AI，自己一个问题都答不上来。它是"总台/中间人"，真正思考和回答的是它背后转接的 DeepSeek、ChatGPT 等大模型。它的价值是让你**用一套方式、安全、方便地**用上所有这些 AI。

**Q3：前端为什么不直接调用 DeepSeek，非要绕一层？**
三个关键原因：
1. **密码安全**：直接从网页调用就必须把消费密码写进网页，任何人按 F12 都能偷走并盗刷；放在后端，用户永远接触不到。
2. **一处对接，随时换 AI**：前端只认识总台。今天用 DeepSeek，明天换成 Kimi，只改通讯录一个词，前端零改动。
3. **统一管理**：日志、用量统计、限流、故障兜底都能在总台统一做。

**Q4：API Key 到底是什么？泄露了怎么办？**
它是 AI 厂商发给你的一串密码（形如 `sk-xxxx`），程序拿着它证明"我是付费用户"，厂商按调用量从你的账户扣钱。泄露了等于把银行卡密码给了别人。**应对措施**：立刻去厂商官网把旧 Key 作废（删除/吊销），生成新 Key 填回 `.env`；这也是为什么本项目坚持把 Key 锁在后端。

**Q5：token 是什么？为什么按它计费？**
AI 不按"字"而按 token 计数。你可以粗略理解为"切碎的语言片段"：英文里一个词约 1～2 个 token，中文一个字常常算 1～2 个 token。输入和输出都会计。回复袋里的 `usage` 就是账单明细。

### 关于"怎么用"

**Q6：`mode` 和 AI 的型号名为什么不总是一样？**
`mode` 是**你自己项目内部**起的套餐代号，可以随便起得好记；真正发给厂商的型号写在通讯录的 `model` 字段里。这样做的好处是：哪天厂商给型号改了名，你只改通讯录里的 `model`，所有老顾客手里的代号完全不用变。

**Q7：单轮 `prompt` 和多轮 `messages` 有什么区别？**
- `prompt`：一问一答，适合"帮我翻译这句话"这类孤立问题；
- `messages`：把之前的对话历史一起按顺序递进去，AI 才"记得上下文"。
  例如先问"我叫小明"，再问"我叫什么？"——只发第二句时，没有历史的 AI 是答不上来的。
两个都填时，系统优先使用 `messages`。

**Q8：temperature 到底怎么调？**
- 0～0.3：严谨、稳定、可重复。适合事实问答、代码、合同、数学；
- 0.4～0.9（默认附近）：平衡，日常聊天、通用写作；
- 1.0～1.5：发散，适合头脑风暴、广告创意、诗歌；
- 1.5 以上：容易天马行空甚至胡言乱语，慎用。
另外不同厂商对取值范围支持不同，本项目质检员统一限定 0～2。

**Q9：为什么 `stream: true` 不能用？**
当前版本只实现了"等整道菜做好再端上桌"的模式；"逐字往外蹦"的流式模式（打字机效果）需要额外的持续通道（SSE），项目已预留了这个开关——传 `true` 会收到明确的 501 提示而不是莫名其妙地失败，后续迭代时再开放。

**Q10：本地模型不要钱、还保密，那为什么不全都用本地的？**
本地模型需要**你自己的电脑有足够的硬件**（很多模型需要较好的显卡和大内存），且同尺寸下能力通常弱于一线商业大模型。所以实践中常见组合是：日常复杂任务用云端商业模型，敏感/高频简单任务走本地模型。本项目让你可以随时在两者间切换。

### 关于"出了问题"

**Q11：启动时报 `No module named 'xxx'`（找不到某个工具）怎么办？**
99% 是没在项目的虚拟环境里运行。确认两点：①已执行过第 4.1 节的安装命令；②运行时用的是 `.\.venv\Scripts\python.exe` 而不是直接敲 `python`。

**Q12：启动时报"端口 8000 被占用"怎么办？**
说明 8000 号窗口已经被别的程序（或上一个没关干净的本项目）占着。二选一：关掉占用它的程序；或改窗口编号——打开 `run.py`，把 `port=8000` 改成比如 `port=8010`，之后所有地址中的端口号同步替换。

**Q13：返回 5030"上游服务暂不可用"是什么意思？**
总台成功营业了，但它替你拨打的 AI 厨房电话没人接。云端模型可能是网络问题或厂商临时故障；本地模型通常是**你根本没启动 Ollama**（或地址/端口与通讯录不一致）。先确认厨房本身在营业。

**Q14：返回 5021"认证失败"但我明明填了 Key？**
钥匙本身有问题：填错了、多了空格、Key 已被作废，或者账户欠费。去对应厂商官网核对并重新生成。

**Q15：国外模型为什么必须走 Router？我不能直连吗？**
技术上可以，但直连通常面临网络可达性差、每家都要单独开户和充值、协议差异等麻烦。OpenRouter 这类平台把这些问题打包解决：一个账户、一张卡、一个接口、几十家模型统一计费。本项目把"走 Router"设计成默认策略；将来若要为某家国外 AI 直连，新写一个适配器即可，架构支持。

**Q16：这么多文件夹，我最该先读懂哪几个？**
建议按"请求旅程"的顺序读 4 个文件：
1. `app/api/v1/endpoints/inference.py`（窗口长什么样）
2. `app/schemas/chat.py`（单子怎么算合格）
3. `app/services/inference_service.py`（排班经理的全套调度——全项目核心）
4. `app/adapters/openai_compatible.py`（标准翻译员怎么干活）
读懂这 4 个，整个项目就懂了八成。

**Q17：日志里的 200、404、500 这些数字是什么？**
它们是互联网行业通用的**状态暗号**（HTTP 状态码）：2 开头 = 一切顺利；4 开头 = 顾客这边有问题（如 404 查无此号、422 表格不合格）；5 开头 = 服务端这边出了状况（如 500 内部错误、502 厨房回话异常、503 厨房联系不上、501 功能还没做）。看到错误先看首位数字，立刻知道该怪谁。

**Q18：以后我想加鉴权（让只有登录用户能调总台）、限流（防止有人狂刷），应该怎么加？**
架构已经预留好位置：这类"对所有请求统一生效"的规则写在 `app/main.py` 的**中间件**里即可（现在那里已经有一个"发追踪编号"的中间件作示范），所有窗口自动生效，业务代码不用动。

## 7. 附录：术语小词典

| 术语 | 一句话解释 |
| --- | --- |
| 后端服务 | 在服务器上默默运行、给其他程序提供服务的程序 |
| 前端 | 用户直接看到和操作的界面 |
| API | 程序之间办事的标准窗口与规矩 |
| API Key | 使用付费 AI 服务的密码，必须保密 |
| 大模型/模型 | 能对话的人工智能及其具体型号 |
| mode | 本项目内部给模型套餐起的代号 |
| 路由 | 按代号查到该找哪家 AI 的转接动作 |
| Router（OpenRouter） | 统一代购国外 AI 的第三方平台 |
| 适配器 | 专管某一家 AI 对接规矩的"翻译员"模块 |
| OpenAI 兼容协议 | 大多数 AI 厂商共同遵循的一套标准说话格式 |
| 路由表 `routes.json` | 套餐代号与厨房的对照通讯录 |
| 注册表 | 翻译员花名册，新翻译员上岗在此登记 |
| Pydantic | 自动检查输入表格是否合规的工具 |
| JSON | 程序间通用的标签式表格格式 |
| token | AI 计量与计费的语言片段单位 |
| 环境变量 / `.env` | 存放密码和设置的配置文件 |
| 虚拟环境 venv | 项目专用、互不干扰的工具间 |
| 端口 | 一台电脑上各服务的窗口编号（本项目 8000） |
| HTTP 状态码 | 2xx 成功 / 4xx 顾客问题 / 5xx 服务端问题 |
| 中间件 | 对所有进出请求统一生效的关卡（如发追踪号） |
| Swagger UI | `/docs` 自动生成的可交互在线说明书 |
| 流式（stream） | 回答像打字机一样逐字返回的模式（本项目预留未开放） |
